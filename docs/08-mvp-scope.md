# 08. 학기 프로젝트용 최소 범위 (MVP) — 당타

> 대상: 객체지향 프로그래밍 수업 팀 프로젝트 · 팀 6명(백엔드 4 / 프론트 2) · **1학기 안에 완성**
> 전제: 팀장(백엔드 1명)만 Spring Boot 경험 있음. 나머지 5명은 Spring / React·Next.js 처음.
> AI 보조(바이브 코딩) 사용 가정.

---

## 1. 결론

| 범위 | 학기 내 완성 가능? |
|---|---|
| **전체 기획(문서 01~07 전부)** | ❌ **불가능**. 8개 도메인 · 40여 테이블 · 실시간 채팅 · 푸시 · 관리자 · S3 · Redis. 경력 있는 소규모 팀이 풀타임 3~6개월 걸리는 분량. |
| **이 문서의 MVP 범위** | ⚠️ **조건부 가능**. 아래 조건을 지키면 "작동하는 데모 + 발표"까지 도달 가능. |
| **초미니멀(§8)** | ✅ **안전하게 가능**. 일정이 밀리면 여기로 축소. |

### "조건부 가능"의 조건 (하나라도 깨지면 위험)

1. **1주차에 범위를 고정**하고 학기 중 기능 추가 금지 (제일 흔한 실패 원인).
2. **팀장이 아키텍처·코드리뷰·통합·배포·인증**을 책임진다. 팀장이 기능 하나 붙잡고 있으면 팀 전체가 막힘.
3. **AI가 짠 코드는 팀장(또는 이해한 사람)이 리뷰 후 머지.** 아무도 이해 못 하는 코드가 쌓이면 OOP 수업 평가(설계·구조)에서 점수를 잃고, 버그를 못 고친다.
4. **"출시 가능한 서비스"가 아니라 "시연 시나리오가 도는 데모"**를 목표로 한다.
5. 실제 배포는 1대(무료 티어) + 로컬 파일 저장이면 충분. 인프라에 시간 쓰지 않는다.

### 바이브 코딩에 대한 현실적인 평가

- **잘 되는 것**: CRUD 보일러플레이트, DTO/엔티티/리포지토리 생성, 기본 화면 컴포넌트, 테스트 뼈대. → 초심자도 속도가 붙는다.
- **안 되는 것**: 6명의 코드가 서로 안 맞을 때 원인 찾기, Spring Security 설정, 배포 트러블슈팅, "왜 CORS 나지", 실시간/동시성. → 여기서 시간이 다 녹는다.
- 결론: **팀장 1명 + AI**면 MVP는 현실적. 팀장 없이 AI만으로는 매우 어렵다.

## 2. 왜 전체 범위는 무리인가 (수치 근거)

| 항목 | 전체 기획 | 학기 프로젝트 현실 |
|---|---|---|
| 실제 개발 가능 기간 | — | **약 8주** (프로젝트 배정 ~중간고사 2주 제외 ~기말·발표 전) |
| 도메인 수 | 8 (거래·중고책·소모임·커뮤니티·채팅·매너온도·시간표·알림) | 8주에 초심자 팀이 소화 가능한 건 **2~3개** |
| DB 테이블 | 40+ | 12~15 |
| 실시간 채팅(STOMP/WebSocket) | 필수 | 인프라·디버깅 난이도 높음 → **폴링으로 대체** |
| 이미지 업로드 | S3 presigned | 로컬 저장 or 단일 업로드 API |
| 캐시/세션 | Redis | DB / 인메모리 |
| 배치(핫게·온도회귀·집계) | 스케줄러 | 조회 시 계산 or 생략 |
| 관리자 도구 | 별도 화면 | DB에서 role 수정 정도 |
| 학기 프로젝트 1인 실질 투입 | — | 주 6~10시간 (타 수업 병행) → 팀 전체 주 40~60시간 |

8주 × 팀 50시간 ≈ **400 man-hour**. 초심자 러닝커브(학습에 30~40% 소모)를 빼면 순수 개발은 **240~280시간**. 전체 기획은 이 예산의 5~10배가 필요하다.

## 3. MVP 범위 정의

### 3.1 포함 (이것만 만든다)

| # | 기능 | 범위 | 담당 |
|---|---|---|---|
| M1 | **회원 / 인증** | 학교 이메일 + 비밀번호 가입, 이메일 도메인으로 대학 자동 매칭, 로그인(JWT 1종·리프레시 없음), 내 프로필 조회/수정 | BE-1(팀장) + FE-1 |
| M2 | **중고거래** | 상품 등록(이미지 1~3장)·목록·상세·수정·삭제, 키워드 검색, 카테고리 필터, 거래상태(판매중/예약중/거래완료), 찜 | BE-2 + FE-1 |
| M3 | **커뮤니티** | 게시판 1~3종, 글 CRUD, 댓글(1단계), 좋아요, 익명 옵션 | BE-3 + FE-2 |
| M4 | **문의 채팅(폴링)** | 상품에서 "채팅하기" → 1:1 방, 텍스트 메시지, 3~5초 폴링으로 갱신, 안읽음 표시 | BE-4 + FE-2 |
| M5 | **매너온도(간소화)** | 가입 시 36.5, 거래완료 후 상대에게 좋았던 점 태그 선택 → 고정 규칙으로 온도 가감, 프로필에 표시 | BE-4 + FE-2 |
| M6 | **공통** | 반응형 모바일 레이아웃(탭바 4개: 홈·커뮤니티·채팅·마이), 신고 버튼(값만 저장), 시드 데이터 | 전원 |

> 탭은 4개로 축소: **홈(중고거래) / 커뮤니티 / 채팅 / 마이**. 중고책·모임·시간표 탭 없음.

### 3.2 제외 (하지 않는다 — 문서에만 남김)

- 중고책(도서 마스터·강의 태그) → **중고거래 카테고리 "책"으로 대체**
- 소모임 전체
- 시간표 전체
- 실시간 WebSocket, 타이핑 표시, 이미지 채팅
- 푸시 알림(웹푸시) · 이메일 실제 발송 → **개발 모드: 인증코드를 화면/로그에 표시**
- 관리자 화면, 신고 처리 워크플로우, 제재
- 매너온도 하락 회귀 배치, 핫게시판 배치, 재거래희망률
- 끌올, 가격 제안, 약속잡기 카드, 스크랩, 투표, 대댓글
- S3 presigned, Redis, 무한스크롤(페이지 번호로 충분)
- 학기 여러 개, 대학 여러 개(1개 대학만 시드)

## 4. 기술 단순화 지침

| 원래 계획 | MVP 대체 | 이유 |
|---|---|---|
| PostgreSQL | PostgreSQL 또는 **MySQL / H2(개발)** | 팀에 익숙한 것. H2로 시작하면 설치 0 |
| Redis | 제거 (DB 조회) | 인프라 하나 줄이기 |
| S3 presigned 업로드 | `MultipartFile` 받아 **서버 로컬 폴더 저장**, `/uploads/**` 정적 서빙 | presigned·CORS 이슈 회피 |
| WebSocket(STOMP) | **REST 폴링** (`GET /chat/rooms/{id}/messages?after=`) 3~5초 | 서버 설정·재연결·멀티인스턴스 문제 전부 제거 |
| Access+Refresh 회전 | **Access JWT 1개** (유효기간 길게, 예 7일) | 토큰 갱신 로직 생략 |
| 이메일 발송(SES) | 개발 모드: 인증코드를 응답 JSON / 서버 로그에 노출 | 메일 인프라 불필요 |
| 스케줄러 배치 | 조회 시점에 계산하거나 생략 | 스레드·크론 학습 비용 절약 |
| Next.js App Router (SSR) | **Next.js지만 거의 CSR로**, 또는 Vite + React SPA도 가능 | SSR·서버컴포넌트 개념까지 갈 여유 없음 |
| Vercel + AWS | **한 대(Render/Railway/학교서버) + Vercel**, 또는 로컬 시연 | 배포에 1주 이상 쓰지 않기 |

권장 스택(축소판): Spring Boot 3 + Spring Web + Spring Data JPA + Spring Security(JWT) + H2→MySQL / 프론트 Next.js(CSR 위주) 또는 React SPA + fetch + 간단한 상태관리(Context/zustand).

## 5. 팀 역할 분담 (6명)

| 역할 | 담당 | 주요 책임 |
|---|---|---|
| **BE-1 / 팀장** | (안민영) | 프로젝트 셋업, 공통 설정(Security·예외·CORS·응답 포맷), 인증(M1), DB 스키마 총괄, **코드 리뷰·머지·통합·배포**, 막힌 팀원 지원 |
| **BE-2** | 중고거래(M2) 도메인 — 엔티티/서비스/컨트롤러, 검색, 상태 전이, 이미지 업로드 API |
| **BE-3** | 커뮤니티(M3) 도메인 — 게시판/글/댓글/좋아요, 익명 처리 |
| **BE-4** | 채팅(M4) + 매너온도(M5) — 폴링 API, 온도 계산 서비스 |
| **FE-1** | 인증 화면 + 중고거래 화면 + **공통 레이아웃·컴포넌트(디자인시스템)** |
| **FE-2** | 커뮤니티 화면 + 채팅 화면 + 마이페이지 |

- 백엔드 4명은 **도메인별로 세로로 분리**(엔티티→서비스→컨트롤러 한 사람이) → 초심자에게 병렬 작업 가장 안전.
- 프론트 2명도 **화면 단위로 분리**, 공통 컴포넌트는 FE-1이 먼저 만들고 공유.
- API 규격(경로·요청·응답)은 문서 04를 축소해 **1주차에 먼저 합의** → BE/FE 병렬 가능.

## 6. 주차별 일정 (8주 실질 개발 기준, 앞뒤로 여유 2주)

| 주차 | 목표 | 산출물 |
|---|---|---|
| **0 (준비)** | 레포·브랜치 전략(main + 도메인별 브랜치), 스프링/프론트 스캐폴딩, "Hello" 화면이 로컬에서 프론트↔백 연결, ERD 확정(12~15테이블), API 규격 합의 | 모두가 `run` 가능한 저장소 |
| **1** | 인증(가입·로그인·JWT·내 정보), 공통 레이아웃·탭바, 시드 데이터(대학 1·카테고리·게시판) | 로그인하면 빈 홈 진입 |
| **2** | 중고거래 BE CRUD + 목록/상세 화면, 이미지 업로드 | 상품 올리고 목록에서 보임 |
| **3** | 중고거래 검색·필터·상태변경·찜, 커뮤니티 BE 시작 | 거래 흐름 완성 |
| **4** | 커뮤니티 글·댓글·좋아요·익명 BE+FE | 게시판이 돈다 · **중간 점검/데모** |
| **5** | 채팅(폴링) BE+FE, 채팅방 생성·메시지 | 두 계정이 대화 가능 |
| **6** | 매너온도(거래완료→평가→온도), 프로필 화면, 신고 버튼 | 거래 후 온도 변동 확인 |
| **7** | **통합·버그픽스**, 시연 시나리오 리허설, 배포(또는 로컬 시연 확정), 에러·빈 상태 처리 | 끊김 없는 데모 경로 |
| **8** | 발표 자료, README, 코드 정리(네이밍·주석·미사용 제거), 시연 영상 | 제출물 |

> 중간고사 주간이 W3~4쯤 겹치면 그 주는 "붙이지 말고 유지보수만". 일정이 밀리면 **W5의 채팅을 제일 먼저 잘라내고**(§8), 매너온도는 "좋아요/별로예요 버튼 + 숫자"로 더 줄인다.

## 7. OOP 수업 대비 — 설계에서 점수 따는 포인트

수업 평가가 "동작"보다 **클래스 설계·객체지향 원칙**을 본다면, 축소된 범위에서도 다음을 의도적으로 보여준다.

- **계층 분리**: Controller / Service / Repository / Domain(Entity) — 책임이 섞이지 않게.
- **값 객체(Value Object)**로 도메인 개념 캡슐화:
  - `SchoolEmail` (도메인 검증·대학 추출), `Money`(원 단위·음수 불가), `MannerTemperature`(0~99 범위·가감 규칙 내장), `Nickname`.
- **enum + 행위**: `TradeStatus`(ON_SALE→RESERVED→SOLD 허용 전이를 enum이 판단), `ReportReason`.
- **상태 패턴 or 명시적 전이 메서드**: `Product.reserve()`, `Product.complete()` — 잘못된 전이는 예외.
- **전략 패턴**: `MannerScorePolicy` 인터페이스 → 태그 기반 계산 구현체. "정책이 바뀌어도 도메인은 그대로"를 시연.
- **상속/다형성**을 억지로 넣지 말 것. 억지 상속보다 **합성·인터페이스**가 더 좋은 평가를 받는 경우가 많음. 필요하면 `Post`/`Comment`의 공통 `Writable`(작성자·작성시각·soft delete) 정도.
- **DTO ↔ Entity 분리**, 매핑은 정적 팩토리 메서드(`ProductResponse.from(product)`).
- **예외 계층**: `DomainException` 상속 구조 + `@RestControllerAdvice` 한 곳에서 변환.
- 테스트: 도메인 로직(온도 계산, 상태 전이)만이라도 **단위 테스트** 몇 개 — "테스트 있음"이 평가에 유리.
- 다이어그램: 클래스 다이어그램(주요 도메인) + 시퀀스(거래완료→평가) 1~2장. 문서 03·02의 mermaid를 축소해 재사용.

## 8. 초미니멀 (일정이 무너지면 여기로)

**중고거래 + 커뮤니티 + 인증**만. 채팅·매너온도 삭제.

| 포함 | 인증(가입/로그인), 중고거래 CRUD·목록·상세·상태변경, 커뮤니티 글·댓글, 반응형 레이아웃 |
|---|---|
| 제외 | 채팅, 매너온도, 찜, 검색(목록만), 이미지 여러 장(1장 또는 URL 입력), 익명 |
| 테이블 | `university`, `user`, `product`, `product_image`, `category`, `board`, `post`, `comment` (8개) |
| 기간 | 실질 5~6주 |
| 데모 시나리오 | ① 학교 이메일로 가입 → ② 상품 등록 → ③ 다른 계정으로 목록·상세 확인 → ④ 상태를 거래완료로 → ⑤ 커뮤니티에 후기 글 + 댓글 |

이 범위는 초심자 5명 + 팀장 1명 + AI로 **거의 확실히 완성**된다. 여기서 시작해 시간이 남으면 채팅(폴링)→매너온도 순으로 붙이는 것을 권장한다.

## 9. 요약 권고

1. **처음부터 §3(MVP)로 시작하고, 2주차에 진척을 보고 §8로 줄일지 결정**한다.
2. 전체 기획 문서(01~07)는 "우리가 아는 척이 아니라 실제로 설계했다"는 **발표용 근거·향후 로드맵**으로 쓰고, 구현은 MVP만.
3. 팀장은 기능 개발보다 **통합·리뷰·인증·배포**에 집중. 이게 이 팀 구성에서 성패를 가른다.
4. "완성된 작은 것" > "미완성인 큰 것". 수업 평가도, 포트폴리오도 그렇다.
